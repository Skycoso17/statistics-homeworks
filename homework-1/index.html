An experiment in public-key cryptography

Inside the One-Way Function

An interactive exploration of elliptic-curve scalar multiplication, the operation that turns an Ethereum private key into a public key.

01The problem

How can a key be public and secret at the same time?

Every Ethereum (or Bitcoin) account is controlled by a single secret number, the private key k. From it the wallet computes a public key Q, and from Q the address that you give to people who want to send you money. Everybody can see Q and the address. Only the owner knows k, and only k can sign a transaction that spends the funds. The whole system works only if one thing is true: knowing Q must not reveal k.

An everyday analogy

Mixing two paints is easy; separating them again is practically impossible. Elliptic-curve multiplication behaves the same way. Going from k to Q takes a few hundred operations on a laptop. Going from Q back to k, with the best known methods, takes about 2¹²⁸ operations: even at a billion billion operations per second that is around 10¹³ years, hundreds of times the age of the universe.

This is the Elliptic Curve Discrete Logarithm Problem (ECDLP): given Q and G, find k such that Q = kG.

Where it is used in practice

  • Crypto wallets. Whoever learns k owns the account. Billions in Ethereum and Bitcoin rely on this one step.
  • Digital signatures (ECDSA). You prove you know k without ever revealing it.
  • Secure connections. HTTPS and messaging apps use elliptic curves to agree on shared secret keys (ECDH).
What we study here. We look at this function as statisticians. If we feed it many keys, what do the outputs look like? Are they uniform, correlated with the input, sensitive to small changes like a hash function? And is “looking random” what makes it secure? To see every value we use a toy curve with 18 points instead of about 10⁷⁷. It is completely insecure, but it works exactly like the real one.
02The idea

Jumping is easy, counting the jumps is hard

Think of G as a fixed jump on the curve. The public key Q = kG is where you land after k jumps. With ordinary numbers this could be undone at once: 6 × 5 = 30, and 30 ÷ 5 = 6. On an elliptic curve over a finite field there is no division of points. The multiples of G land in an order that looks scrambled, so seeing where you ended tells you nothing about how many jumps you made. The only general method is to search.

Ordinary multiplication keeps the order

The value 5·k grows steadily with k. Given the result, k is found with one division.

Point multiplication scrambles it

The x-coordinate of kG jumps around with no trend. There is no “bigger means more jumps” to exploit.

The asymmetry in numbers

The forward direction uses the binary digits of k, so its cost grows with the number of digits (log₂ n). Going backwards costs about √n even with the best known algorithm (Pollard’s rho). The gap explodes as the group grows.

03The algorithm

From adding two points to computing kG

Step 1

Adding two points: the chord-and-tangent rule

Over the real numbers the curve y² = x³ + 7 is a smooth line, and any straight line crosses it in three points. To add P and Q: draw the line through them, find the third intersection −R, then reflect it across the x-axis to get R = P + Q. To double a point (P + P) the line is the tangent at P. A vertical line meets the curve “at infinity”: that extra point O works like zero, so P + (−P) = O.

Step 2

The same rule, with arithmetic modulo 17

Cryptography cannot use real numbers (rounding errors, infinite precision), so every coordinate is an integer from 0 to 16 and every result is taken modulo 17. The geometry disappears but the formulas stay the same:

λ = (y₂ − y₁) / (x₂ − x₁)    slope of the line P–Q
λ = (3x₁² + a) / (2y₁)       slope of the tangent (P = Q)
x₃ = λ² − x₁ − x₂
y₃ = λ(x₁ − x₃) − y₁         every result mod 17, a = 0

Division is a modular inverse. “1 / 10 mod 17” is the number that multiplied by 10 gives 1: it is 12, because 10 · 12 = 120 = 7 · 17 + 1. We find it with the extended Euclidean algorithm.

Step 3

From addition to multiplication: kG

Repeated addition computes G, 2G, 3G, …, kG: k − 1 additions. Simple, but useless for a 256-bit k.

Double-and-add reads k in binary, from the left. For every bit it doubles the current point, and when the bit is 1 it also adds G. The number of operations is about twice the number of bits.

Worked example: k = 6 = 110₂

05Statistical exploration

What can we observe in the public points?

We repeat Q = kG for different keys, count what appears, and draw a few graphs. Every experiment follows a clear path: what we do, what the numbers show, and what we can conclude. We also repeat measurements with new keys where it makes sense.

Repeat the experiment with different keys and base points

The animation in section 04 uses the original example G = (1, 5), k = 6. The experiments below use your selected base point.

1
Coordinate distributions · value frequencies

Which X and Y values appear, and how often?

First we generate all the different finite public points and count which X and Y values occur. Then we use 240 random keys to see how these same coordinates occur when we repeat the process. The graphs show the possible values, while the tables explain the numbers.

2
Apparent uniformity

Why do we sample random keys, and what can we learn?

We randomly choose 240 private keys between 1 and the order of G minus 1 (repetitions are allowed). We then compute each public point. Purpose: compare how often each point actually appears with how often we would expect it to appear if all keys are equally likely. A small table makes this easy to check.

3
Bit distribution

Are the bits in X and Y balanced?

A public point has two coordinates, X and Y. We write each value using 5 bits (for example, 5 = 00101). First we read the binary representation of all distinct finite points. Then we enlarge the observation to 240 randomly sampled keys, allowing repeated points. We compare the percentage of 1s in each bit position with the exact percentage. This makes it easier to see which bits are more common and why.

4
Avalanche-like behaviour

What happens when one input bit changes?

We start with two valid keys that differ by one bit and watch the difference spread through their public-point representations. The animation shows one example; a short table also compares all valid one-bit key pairs on this small curve, so our observation does not rely on one example alone.

07Conclusion

What does all this tell us?

Our experiments show that multiplying a key by a point is a predictable mathematical operation, but the resulting coordinates and bits can look irregular. By collecting and comparing data, we learned how the outputs are distributed, how often they appear, and what happens when we slightly change the input.

What matters for our algorithm? None of these observations alone tells us whether the algorithm is secure. The real purpose of elliptic-curve multiplication is that calculating a public point from a private key is easy, while finding the private key from the public point should be extremely difficult on a suitably large curve.
