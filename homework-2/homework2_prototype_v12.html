01 / Introduction

One phrase. Many addresses.
How is that possible?

A wallet needs private keys to sign transactions, public keys to verify signatures, and addresses that people can use to receive funds. Memorizing a separate private key for every account would be inconvenient and risky.

Modern hierarchical deterministic wallets solve this with a recoverable starting point: a mnemonic phrase. Several standards and cryptographic functions then transform it into a family of reproducible keys and addresses.

THE QUESTION

Can we reproduce the result?

Same mnemonic, optional passphrase and derivation path → same derived account.

THE SECURITY

Can we reverse it?

Public keys and addresses should not make recovering their private keys computationally feasible.

THE STATISTICS

What looks random?

We can measure output changes, compare averages, and discuss probabilities without advanced statistical tests.

02 / Historical and temporal context

How did we get from cryptography to wallets?

An Ethereum wallet is not the result of one invention. It brings together decades of research: first, ways to prove ownership without sharing a secret; then, ways to transform data securely; finally, Bitcoin-era standards that made large collections of keys easier to recover and manage. Ethereum reused many of these ideas and added its own address format.

Foundation · 1977–2001

Two different needs: proving identity and hashing data

Before blockchain wallets existed, public-key cryptography answered an essential question: how can someone prove control of a secret without revealing it? In 1977, RSA helped establish the practical use of public and private keys. Much later, secure hash functions addressed a different need: producing a short, fixed-size fingerprint of data. The SHA-2 family, including SHA-512, emerged around 2001 and was standardized in the early 2000s.

1977RSAA historical milestone for public-key cryptography. Ethereum does not use RSA for account keys: it uses elliptic curves instead.
2001SHA-2 / SHA-512A new family of cryptographic hashes. SHA-512 later became part of the BIP-39 and BIP-32 key-derivation processes through HMAC.
Wallet design · 2012–2014

From many unrelated keys to one recoverable wallet

Early cryptocurrency wallets could be difficult to back up: each newly generated independent key might need to be saved. The hierarchical deterministic (HD) approach changed that. Instead of storing unrelated keys, a wallet could produce a whole family of keys from one starting seed. Mnemonic phrases then made that starting point easier for people to record; standardized paths made it easier for different software to locate the same accounts.

2012BIP-32Introduces deterministic key trees: one seed can lead to many child keys.
2013BIP-39Introduces mnemonic codes, representing entropy in words and deriving a seed. Although proposed after BIP-32, it appears first when a user creates a wallet.
2014BIP-44Adds a shared organization for purposes, coins, accounts and address indexes within the BIP-32 tree.
Ethereum era · 2015–2016

From public keys to readable Ethereum addresses

Ethereum launched in 2015 and adopted secp256k1 elliptic-curve keys, as Bitcoin had done. It derived account addresses using Keccak-256, taking only 20 bytes from the resulting digest. The public address was convenient to share, but a copied hexadecimal string could contain unnoticed typos. EIP-55 later added mixed-case error detection.

2015SHA-3 standardNIST standardizes a hash family based on Keccak. Ethereum's Keccak-256 is closely related but differs from standardized SHA3-256.
2016EIP-55Proposes using letter capitalization in hexadecimal Ethereum addresses as a lightweight checksum.
Two names that must not be confused: SHA-512 is from the SHA-2 family and helps derive the wallet seed/keys; Keccak-256 hashes the public key to help form an Ethereum address. The later NIST SHA3-256 standard uses a Keccak-based design, but different domain-separation/padding rules mean that Keccak-256 and SHA3-256 produce different outputs.
03 / How a wallet is created

From a recovery phrase to a public Ethereum address.

When you create a new Ethereum wallet, the process begins by generating a secret mnemonic (recovery) phrase from random data. The wallet then follows a sequence of steps called a derivation pipeline: it turns the phrase into a seed, derives a private key for an account, calculates the corresponding public key, and finally produces a public Ethereum address that others can use to send you funds. The six technologies below each play a different role in this journey. Follow them from top to bottom; in the next section, we will repeat the same pipeline with real numbers.

This describes the usual creation of a new software wallet. Restoring an existing wallet starts from a previously saved mnemonic instead of generating a new one. The mnemonic and private keys must remain secret; the public address can be shared.

01
MNEMONIC ENCODING + SEED GENERATION

BIP-39 — From randomness to a recovery phrase

The wallet starts with random entropy. BIP-39 encodes it into a list of familiar words, including a small checksum. Then PBKDF2-HMAC-SHA512 converts the words (and an optional passphrase) into a 512-bit seed. Why? People can back up words more easily than raw binary keys.

12 words → 512-bit seed
Output: seed ↓
02
HIERARCHICAL KEY DERIVATION

BIP-32 — From one seed to many keys

BIP-32 builds a deterministic tree of keys using HMAC-SHA512 and chain codes. The same seed always creates the same tree. Why? One backup can recover many accounts rather than only a single private key.

seed → master key → child keys
Output: a hierarchy of possible keys ↓
03
DERIVATION PATH CONVENTION

BIP-44 — Which key in the tree?

BIP-44 does not create a new cryptographic algorithm: it tells wallets how to organize and find accounts within the BIP-32 tree. Ethereum's coin-type number is 60. Why? Wallet software needs an agreed path to locate the same account.

m/44'/60'/0'/0/0 → first key in this example
Output: selected private key ↓
04
PUBLIC-KEY CRYPTOGRAPHY

secp256k1 — From private key to public key

A private key is a secret number, while its public key is a point on an elliptic curve. The relationship is Q = k · G: scalar multiplication of a public generator point. This recalls elliptic-curve multiplication from our earlier work. Why? A user can sign transactions without sharing the private key.

private scalar k → public point Q = (x, y)
Output: public key coordinates ↓
05
CRYPTOGRAPHIC HASHING

Keccak-256 — From public key to address

Ethereum hashes the 64 bytes containing the public key's x and y coordinates (without the 0x04 uncompressed-key prefix). It keeps the final 20 bytes of the 32-byte digest. Why? This produces the compact 160-bit Ethereum address. Hashing is not encryption.

64-byte key → 32-byte hash → 20-byte address
Output: lowercase hexadecimal address ↓
06
CHECKSUM + ENCODING

EIP-55 — From address to safer written address

An Ethereum address is typically displayed as hexadecimal text. EIP-55 uses a Keccak-based rule to capitalize some letters. Why? Incorrectly copied or typed public addresses can be detected more easily. It does not change the underlying 20 bytes or protect against every possible typo.

0x + 40 hex characters → mixed-case representation

05 / Statistical properties

What can we actually measure?

We have followed the wallet pipeline from the recovery phrase to the public address. Now we explore five statistical properties that help us understand what happens to the numbers along the way. Each experiment follows the same simple path: what the property means → what we observe → what this means for our Ethereum wallet.

01 — ENTROPY · NUMBER OF POSSIBILITIES

How many recovery phrases could exist?

A standard 12-word BIP-39 phrase comes from 128 randomly generated bits. Each extra random bit doubles the number of possibilities. Four more checksum bits help detect invalid phrases; they do not add randomness.

1 · What is entropy? Entropy describes how hard it is to predict a randomly generated secret. One fair random bit has two possibilities; every additional random bit doubles the search space.

2 · What do we observe? In our BIP-39 example, a 12-word phrase represents 128 random bits: that is 2128 ≈ 3.4 × 1038 possible original secrets. The extra four mnemonic checksum bits do not increase this number. Our specific public test phrase is already known, so it has no secrecy.

3 · What does this mean for the wallet? A securely generated phrase is extraordinarily difficult to guess. Since BIP-32 deterministically derives every later key from the seed, the security of the entire wallet starts with good randomness. Turning it into a 512-bit seed does not create additional original entropy.

02 — AVALANCHE EFFECT · LIVE COMPARISON

What happens when we change just one bit?

Think of a hash as a digital fingerprint. We change one bit of its input, recalculate Keccak-256, and compare the fingerprints. Ideally, this tiny change affects about half the output bits on average. The green squares below are changed output bits; the dark squares are unchanged.

1 · What is the avalanche effect? A good cryptographic hash spreads a tiny input change across many output bits. If we flip just one input bit, we expect about half of the 256 output bits to differ on average across many tests.

3 · What does this mean for the wallet? In the Keccak-256 stage, even a very small change to the public-key input produces a very different hash, rather than a slightly modified one. That is useful for producing addresses that do not reveal simple patterns from similar inputs. It does not, by itself, prove the hash is secure.

03 — HAMMING DISTANCE · REPEAT THE EXPERIMENT

Does the same pattern appear across many tests?

The Hamming distance is simply the number of positions at which two bit strings differ. For a 256-bit hash, the ideal average is 128 changed bits.

Fewer bits changedAround 128More bits changed

1 · What is Hamming distance? It is simply a count of how many bit positions differ between two equally long outputs. It gives us a numerical way to measure the avalanche effect.

2 · What do we observe? We repeated the one-bit-input-change test 1,200 times. The mean was 128.33 changed bits out of 256 (50.1%), close to the ideal mean of 128 (50%). The standard deviation was 8.06 bits, so individual results naturally vary. The histogram shows how often different distances appeared.

3 · What does this mean for the wallet? Keccak-256 showed the expected strong mixing on this test set. The key statistical lesson is that 50% is an expectation, not a rule for every trial. The experiment supports the avalanche observation but cannot establish full cryptographic security.

04 — COLLISIONS · BIRTHDAY INTUITION

Could two different keys produce the same address?

Imagine assigning random birthdays: duplicates become more likely as the number of people grows. Hashes behave similarly in the ideal model, but their output space is enormous.

Full Keccak-256 hash: 2256 possible outputs; roughly 2128 attempts for a substantial chance of any collision.

Ethereum address: keeps only 160 bits, so collision calculations for addresses use 160 bits, not 256.

1 · What is a collision? Two different inputs give exactly the same hash (or address). A finite output space makes collisions mathematically possible.

2 · What do we observe or calculate? Rather than trying an impossible number of wallet addresses, we use the birthday paradox. In the ideal model, any collision among full 256-bit hashes becomes plausible only around 2128 random trials. Ethereum keeps 160 bits for the address: address-collision calculations instead use about 280 trials for a substantial birthday-collision chance.

3 · What does this mean for the wallet? Different public keys could theoretically lead to the same 160-bit address, but accidental collisions are extraordinarily unlikely at small practical scales. These are theoretical probability estimates, not collisions we observed in our experiment.

A collision means two different inputs lead to the same output. This is different from guessing one particular private key.

05 — EIP-55 · ERROR DETECTION

Can the wallet detect a typing mistake?

An address uses hexadecimal digits. EIP-55 adds a capitalization pattern derived from a hash so a wallet can notice many accidental typing errors.

1 · What is a checksum? A checksum adds a way to check whether data has probably been mistyped or changed. EIP-55 uses capital and lowercase hexadecimal letters to encode this check.

2 · What do we observe? Click Introduce capitalization error above. One letter changes case, and the EIP-55 check fails. This is a direct demonstration of an error being detected, not an encryption operation.

3 · What does this mean for the wallet? The same 160-bit Ethereum address becomes safer to copy and read because many typing errors are rejected. The EIP gives an average false-acceptance rate of approximately 0.0247% for randomly mistyped addresses; it does not detect every mistake or protect a stolen private key.

What did statistics add to our pipeline? Entropy helps explain why the starting secret must be unpredictable. Avalanche effect and Hamming distance let us observe how Keccak-256 responds to a tiny change. Collision probability describes how unlikely repeated addresses are under an ideal model. The EIP-55 checksum demonstrates error detection in the final written address. Different properties answer different questions—none replaces the others.
06 / Conclusions

One wallet, several kinds of security.

Our guided test demonstrates a reproducible path from a mnemonic to an Ethereum address. BIP-39, BIP-32 and BIP-44 handle recovery and deterministic key management; secp256k1 connects private and public keys; Keccak-256 converts the public key into an address; EIP-55 helps detect human transcription errors.

The statistical experiment shows that a tiny input change can produce a large, approximately balanced change in the 256-bit output. Entropy helps explain the enormous space of possible secret values; collision probabilities and checksums address different kinds of risk. No single algorithm could replace every stage because each stage solves a different problem.

Final takeaway: Determinism makes wallets recoverable; strong cryptographic primitives make their keys difficult to attack; statistical properties help us understand their behavior.
