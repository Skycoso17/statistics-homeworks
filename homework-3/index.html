Can we protect a message?

Previously, we explored elliptic-curve scalar multiplication: take a private integer k, multiply the generator point G, and obtain a public point Q. That experiment showed us how to obtain a public key from a private key. But it did not encrypt any data. If we send a message without encryption, an adversary who intercepts it can read its contents. How can we use what we learned about ECC to protect a message? That is the problem we address next.

What exactly is cryptography?

Cryptography is the study of methods for protecting information. For confidentiality, an encryption algorithm takes a readable message (plaintext) and a key and produces an unreadable representation (ciphertext). A corresponding decryption algorithm uses the appropriate key to recover the original message.

What should remain secret?

In Caesar, the shift key must be secret for the intended toy model. In ECC, Bob keeps k private; G and Q are public. The data we want to hide is the message itself.

Is an encrypted message always safe?

No. Encryption may work correctly but still be easy to break. Security depends on the algorithm, its parameters, the available keys, and how it is used. We will test this experimentally.

EXPERIMENT 01 · UNDERSTANDING ENCRYPTION

The Caesar cipher: one key, one shift.

Caesar is a substitution cipher: replace every letter with another letter a fixed number of positions later in the alphabet. That number is the key. To decrypt, move each letter backward by the same amount. It is a simple example of symmetric encryption because sender and receiver use the same key.

FIRST, WATCH ONE LETTER

Number the letters from A = 0 through Z = 25. With key 3, A moves three positions forward and becomes D.

A+3 →DWhen we reach Z, we return to A: X + 3 → A.
Encrypt: C = (P + key) mod 26
Decrypt: P = (C − key) mod 26

mod 26 simply means “wrap around after 26 letters”. For example, X = 23, so (23 + 3) mod 26 = 0, which corresponds to A.

What question comes next?

THE CENTRAL QUESTION OF HOMEWORK 02

We know how ECC creates public keys. How do we use that process to turn a readable message into encrypted data — and back again?

We will distinguish the mathematical ECC step from the actual byte-encryption step. Follow the chain below: key generation → shared point → byte encryption → transmission → decryption.

UNDERSTAND THE DIFFERENCE FIRST

What ECC key generation does

Bob chooses k, calculates Q = kG, and shares Q. The generator G and public point Q can be seen by anyone. k remains secret. This step does not modify the message.

What encryption adds

Alice uses Q and a temporary scalar r to calculate a shared point S = rQ. Bob can reproduce the same point with S = kR, where R = rG. Only after that do we transform the message bytes into ciphertext.

Key distinction: We do not encrypt k, G or Q to make ECC work. G and Q are deliberately public; k must remain private. We encrypt the message. The scalar multiplication supplies material from which an encryption key can be derived.

EXPERIMENT 03 · STATISTICAL PROPERTIES

What does encryption do to the patterns in our data?

We have encrypted the same message with Caesar and with our toy ECC-based scheme. Now we can observe an important difference: what statistical information remains visible in the ciphertext? Here we study the output, before attempting to break either algorithm.

FIRST, TWO DIFFERENT TYPES OF DATA

Caesar transforms letters

Each letter is moved by the same amount. Thus the ciphertext has exactly the same frequency counts as the plaintext, only assigned to different letters. If E appears 10 times, its encrypted replacement also appears 10 times.

Our ECC scheme transforms bytes

ECC first creates a shared point. Our toy byte mask then changes the UTF-8 bytes using XOR. The output is not necessarily readable letters: it can contain any byte value from 0 to 255. Its statistical behavior depends on the mask construction, not on the elliptic curve alone.

WHAT CAN AN OBSERVER INFER?

Caesar leaks language structure

The same plaintext letter always maps to the same ciphertext letter. Repeated letters stay repeated, and a long English text retains a recognizable frequency profile. This gives us the idea for the upcoming statistical attack.

ECC itself does not promise a byte distribution

Our curve operation yields a shared point, while our simplistic deterministic mask produces bytes. The byte patterns you see belong to this specific toy construction. A properly designed encryption system uses a secure key derivation and authenticated encryption, so observing the toy output tells us little about secure ECC-based systems.

EXPERIMENT 04 · GUIDED CRYPTANALYSIS

Can we break Caesar without knowing the key?

Imagine Eve intercepts a Caesar-encrypted text. She knows how Caesar works, but not the shift. Our goal is to recover the original text and the key. We combine two ideas: brute force produces all 26 possible messages, and statistics helps decide which one is probably English.

WHY THIS ATTACK IS POSSIBLE

1. Only 26 keys

Caesar uses a shift between 0 and 25. We can try every shift instead of guessing.

2. Patterns survive

If TURING is repeated, the encrypted version repeats too. If HELLO has two Ls, the ciphertext still has a double letter.

3. English is not random

Letters such as E and T occur much more often than Z. A long enough English message leaves a recognizable statistical signature.

WHY STATISTICS HELPS CHOOSE THE CORRECT KEY

We compare the observed letter frequencies for each candidate with the typical English frequencies. The Chi-square score summarizes their difference. Lower is better: the candidate resembles English more closely.

χ²(k) = Σ (observed − expected)² / expected

On a short ciphertext such as TURING TURING, this score may choose the wrong key: there are too few letters to represent normal English. This is why the message length matters.

OPTIONAL DISCUSSION · WHAT ELSE COULD FAIL?

Restricted key space

When the secret scalar is drawn from a tiny range, brute force succeeds regardless of the language or message length. Increasing the number of possible private keys directly targets this weakness.

Design of the toy encryption scheme

Our demonstration derives a predictable XOR mask from a tiny shared point. That design can reveal patterns and should not be confused with a secure key-derivation function and authenticated encryption. Reusing temporary values or choosing them poorly can create further weaknesses even on a strong curve.

Alternative approaches: Caesar can also be attacked with dictionary checks or n-gram scoring. Generic ECC attacks include baby-step/giant-step and Pollard's rho; they operate on group structure, not letter frequencies. Weak implementation details can introduce vulnerabilities independently of key-space size.
OUR CONCLUSION

Security depends on the information an attacker can exploit.

Caesar exposes statistical information about the original language. Our toy ECC setup exposes a small space of potential private keys. A full-sized ECC private key removes that easy search route, but secure encryption also requires a sound protocol and implementation.

TAKEAWAY

Encryption working ≠ encryption being secure.

The Caesar cipher leaks linguistic structure and has only 26 shifts. Our toy ECC model demonstrates public/private key operations, but its tiny subgroup makes key recovery trivial. Proper security requires sufficient key entropy and a well-designed, authenticated encryption scheme.
